# Specification & Overview

### 1. Scope & Objective
- **Source provenance:** `docs/ROADMAP.md`, section `v0.0.8 - Releases and Captured State Comparison`; `docs/CM-MODPACK-UTIL-SPEC.md`, especially Release Tracking and Version Comparison, Update Snapshots, Changelog Generation, Data and Lifecycle Expectations, Provider and Mod Identity Rules, Domain Concepts and Business Rules, Non-Functional Requirements, Integrations and External Dependencies, Architecture Guidelines, Security and Privacy, Technology Decisions and Rationale, and Workflow Acceptance Criteria; completed `docs/plans/v0.1.0/v0.0.7.md`; repository conventions in `AGENTS.md` and the existing Rust/Svelte module layout.
- **Goal:** Add named release records that capture validated Packwiz state at creation time, retain optional Git provenance, compare releases from their immutable captured evidence, and optionally enrich public GitHub metadata without making GitHub or Git available a prerequisite for local release tracking.
- **In-Scope:**
	- Audit the v0.0.7 changelog/artifact and v0.0.6 snapshot/operation handoffs before introducing release ownership.
	- Define release lifecycle, publication status, release notes/description, optional version/name, optional snapshot association, and captured-state contracts.
	- Capture the complete relevant Packwiz state from a validated registered modpack independently of future working-tree changes, moves, disconnects, or Git availability.
	- Preserve local entry identity, exact metadata paths as observed, mod versions, provider declarations, side declarations, source URLs when available, Minecraft version, loader information, and other validated release evidence needed for later comparison.
	- Record optional Git repository root, branch, exact commit SHA, tag, remote, cleanliness, conflict/rebase evidence, and unavailable provenance states without requiring a commit or clean tree.
	- Allow release creation from an explicitly validated local state, including a visibly provisional release for an eligible partial or failed operation where the source evidence contract permits it; do not represent provisional state as normally publishable.
	- Compare two releases using captured release state rather than the current working tree, showing added, removed, version-changed, provider/source-metadata-changed, Minecraft/loader changes, release notes, associated changelog information, and available commit differences.
	- Expose release listing, detail, creation, editing of application-owned release fields, comparison, and snapshot/changelog navigation through typed Rust/Tauri commands and modular Svelte surfaces.
	- Add focused Rust contracts, parser/comparison/persistence tests, fixture coverage, frontend checks, documentation, and the v0.0.8 exit-gate validation.
- **Out-of-Scope:**
	- Cleanup, archive/restore, detach, permanent deletion, impact previews, storage management, and orphan cleanup reserved for v0.0.9.
	- CurseForge API access, private GitHub authentication, cloud synchronization, collaboration, accounts, unattended updates, automatic rollback, or application-created backups.
	- Replacing Packwiz files, editing TOML directly, checking out historical commits into the active working tree, or making the current database record authoritative for current Packwiz state.
	- Treating a Packwiz-declared version as a release record automatically; a snapshot never becomes a release without explicit user action.
	- Making Git, a clean working tree, a commit, a tag, a remote, or GitHub hosting mandatory for release creation or captured-state comparison.
	- Guessing CurseForge URLs, provider identities, historical file contents, commit relationships, GitHub repository identity, or release publication state from weak evidence.
	- GitHub metadata enrichment and synchronization; this is explicitly deferred until a later milestone after the local release workflow is proven.
	- Non-Markdown export changes, provider cache expiration, or broad release automation.

### 2. Technical Constraints & Architecture
- Packwiz files remain authoritative for current external modpack configuration. A release stores an immutable application-owned observation of validated Packwiz evidence; it never writes current Packwiz state or substitutes for a fresh inventory read.
- SQLite owns release metadata, captured release state, Git provenance observations, comparison inputs/results where persistence is justified, optional GitHub enrichment, and relationships to snapshots/changelog artifacts. Continue the alpha `CREATE TABLE IF NOT EXISTS` policy; do not introduce migrations. Any incompatible local database consequence must use the documented stop-app/reset path rather than silent rewriting.
- Rust owns registered-modpack authorization, local Packwiz reads, validation, state capture, Git inspection, historical Git-object reads if supported, comparison semantics, SQLite transactions, public GitHub requests, URL trust, structured errors, and Tauri command contracts. Svelte owns release selection, forms, comparison presentation, loading/progress/error states, and navigation.
- Keep release domain contracts, state-capture logic, Git provenance, comparison logic, persistence, GitHub transport/enrichment, typed frontend wrappers, and Svelte presentation in separate modules. Do not consolidate all release behavior into `db/mod.rs`, `lib.rs`, or the existing root route.
- Release state must preserve the dual identity model from earlier milestones: local Packwiz entry identity and download-provider evidence remain distinct from Modrinth changelog identity. Existing changelog artifacts remain referenceable without being copied into or confused with release state.
- Release creation must capture current validated state at command time and record the validation/freshness evidence used. The command must re-check registered-modpack ownership and current evidence rather than trusting a frontend snapshot of inventory.
- A dirty Git tree may be recorded with an explicit visible warning; a no-Git modpack remains valid. Conflict, merge, rebase, inaccessible repository, missing commit, and unavailable remote evidence remain explicit observations and do not invalidate captured state unless the user-selected operation specifically requires that evidence.
- Git historical reads must be read-only. Never silently checkout an old commit into the active modpack directory. A temporary isolated reconstruction is permitted only if a later implementation decision proves it necessary and safe; direct captured-state comparison remains the default.
	- GitHub enrichment is deferred from v0.0.8. No GitHub request, imported metadata field, or public-remote dependency is introduced by this milestone.
- Preserve shared UI primitives and standards from `docs/desktop-ui-standards.md`: keyboard access, visible focus, semantic status, reduced-motion behavior, stable layouts, color-independent state, explicit pending/failure handling, and no direct filesystem/network/process access in Svelte.

### 4. Decisions, Assumptions, and Deferred Risks
- **Confirmed handoffs:** v0.0.6 provides immutable snapshots, operations, fingerprints, validated current inventory, and read-only Git status; v0.0.7 provides durable changelog artifacts, immutable revisions, export history, provider evidence, and snapshot-linked generation. Existing modpack registration and path authorization remain the native boundary.
- **Confirmed product rules:** A release is explicit and separate from a snapshot; captured release state is authoritative for release comparison; Git provenance is optional; no commit is required; partial/failed source operations may only produce visibly provisional releases when their captured evidence is valid; local release records work without GitHub.
	- **Decision register closed 2026-09-07:** release creation accepts validated current state plus reviewable, completed, and partial source evidence; captured state uses a versioned canonical allowlist; unstable captures are rejected and retried; comparisons are computed on demand using stable local identity followed by provider identity with ambiguity reported; captured evidence and provenance are immutable while application-owned fields use guarded transitions; Git provenance is captured without historical reconstruction or commit-range inference; GitHub enrichment is deferred; release metadata, capture, provenance, and same-modpack relationships are persisted in one transaction; and provisional releases require a fresh validated capture for promotion.
	- **Assumptions to verify:** the canonical capture allowlist can be populated from validated Packwiz reads without silently dropping comparison-relevant fields; additive tables can represent release-to-snapshot, artifact, and provenance relationships with same-modpack checks; and the current Git status seam can be extended without making Git mandatory.
- **Primary risks:** current files may change during capture; malformed or incomplete evidence may be mistaken for a complete release; dirty trees may be misunderstood as recoverable; a repository may move or lose its commit; release comparison may accidentally read current files; GitHub rate limits or unavailable remotes may block the UI; existing alpha databases may not contain the new tables; and a large captured inventory may make comparison or persistence slow.
	- **Safety response:** revalidate at command time, capture a bounded canonical field set with before/after stability fingerprints, reject unstable reads, keep captured state immutable, separate release status from operation outcome, treat unavailable provenance as non-fatal, use deterministic comparison from stored captures, persist one atomic release transaction, and keep all external file/Git operations read-only.

### 5. Closed Decision Register - 2026-09-07

| ID | Decision | Consequence for implementation |
| --- | --- | --- |
| d1-eligibility | Allow validated current state plus reviewable, completed, and partial source evidence; reject failed, cancelled, unsafe, stale, and disconnected sources. | Add a native eligibility matrix and explicit provisional state; do not infer eligibility in Svelte. |
| d2-capture | Store a versioned canonical allowlist of comparison-relevant Packwiz/runtime/entry evidence, observed paths, field provenance, and a capture fingerprint. | Do not treat the existing inventory projection as complete without defining and testing the allowlist. |
| d3-stability | Reject release creation when the bounded source read changes during capture. | Require before/read/after fingerprinting and a structured retryable error; unstable evidence is not a provisional release. |
| d4-comparison | Compute comparisons on demand from persisted captures; match stable local identity first, provider identity second, and expose ambiguity. | Do not persist derived comparisons or read the current working tree during comparison. |
| d5-editability | Keep capture, provenance, timestamps, fingerprints, and source relationships immutable; allow application-owned fields and guarded status transitions. | Add transition validation and prevent status-only promotion of provisional evidence. |
| d6-git | Capture repository root, branch, HEAD SHA, tag, remote, working-tree state, and conflict/rebase evidence when available; defer historical reconstruction and commit ranges. | Extend the read-only Git adapter without checkout or historical file reconstruction. |
| d7-github | Defer GitHub metadata enrichment from v0.0.8. | No GitHub transport, imported metadata, or remote prerequisite is added in this milestone. |
| d8-persistence | Persist release metadata, immutable capture, provenance, and same-modpack relationships in one SQLite transaction using additive schema initialization. | A release is not returned as successful until all required evidence is durable. |
| d9-provisional | Partial evidence may create a provisional release; promotion requires an explicit fresh validated capture. | Preserve the original provisional capture and make promotion a guarded workflow. |
