# Specification & Overview

### 1. Scope & Objective
- **Source provenance:** `docs/ROADMAP.md`, section `v0.0.5 - Snapshot Review and Decision Tracking`; `docs/CM-MODPACK-UTIL-SPEC.md`, especially Update Discovery and Review, Pins, Skips, and Notes, Update Snapshots, Domain Concepts and Business Rules, Data and Lifecycle Expectations, Architecture Guidelines, Long-Running Work and Errors, and the Partial Outcomes, Identity, and Apply Safety workflow criteria; completed `docs/plans/v0.1.0/v0.0.4.md` as the implementation handoff for discovery evidence and compatibility boundaries.
- **Goal:** Turn the safe v0.0.4 discovery observation into a durable, revisit-able snapshot review workflow. A user must be able to inspect the exact candidates and safety evidence returned by discovery, record explainable decisions and notes without modifying Packwiz files, detect when the reviewed project has changed, close or cancel a session, and retry through a new linked snapshot while preserving the original history.
- **In-Scope:**
	- Define a stable snapshot/session contract with project identity, lifecycle timestamps, optional label, review/closed/cancelled/unsafe/indeterminate states, before-state evidence, discovery outcome, and immutable operation evidence.
	- Persist candidate observations as historical records, retaining local Packwiz entry identity, current/available versions, provider, side, pin evidence, source/page evidence, severity classification, compatibility warnings, and unresolved/unknown values.
	- Persist selected, skipped, blocked, and deferred decisions per candidate, with clear distinction between Packwiz-owned `pin` state and application-owned snapshot decisions.
	- Persist project-level notes and snapshot/decision notes with enough scope to explain why a candidate was skipped, blocked, deferred, or selected.
	- Reopen and list historical snapshots, restore the review state, and show immutable discovery/operation history. Closing or cancelling a review must not discard its evidence.
	- Recheck the stored relevant-project fingerprint before treating a review as current; mark the review stale/invalidated when external Packwiz files change or evidence is incomplete.
	- Create a new linked snapshot for retry after an unsafe, indeterminate, cancelled, or otherwise incomplete session; never overwrite the original attempt or silently reuse stale decisions.
	- Add Rust-owned persistence and Tauri commands, typed TypeScript wrappers, and accessible Svelte review/history states using existing UI primitives.
	- Add focused tests, fixture coverage, documentation updates, and the v0.0.5 exit-gate validation.
- **Out-of-Scope:**
	- Applying updates, sending `y`, Packwiz pin/unpin mutation, direct TOML editing, rollback, or any other change to the external project directory.
	- Changelog generation/export, Modrinth or CurseForge requests, releases, GitHub enrichment, cleanup/permanent deletion, and broad data-management workflows reserved for later milestones.
	- Replacing Packwiz as the authority for current inventory, provider, side, source URL, or persistent pin state; SQLite stores historical observations and decisions only.
	- Guessing provider identity, source URLs, semantic severity, or compatibility facts when the evidence is missing or malformed.
	- Generalizing beyond the tested v0.0.4 Packwiz compatibility profile or treating fixture success as broader live Packwiz compatibility.
	- Introducing a migration framework, network dependency, arbitrary filesystem path handling, frontend shell/process execution, or a second discovery command path without an explicit scope decision.

### 2. Technical Constraints & Architecture
- Packwiz files remain authoritative for current project state. Snapshot records are immutable historical observations plus user decisions; they must not be used to overwrite or silently substitute current local evidence.
- Rust owns snapshot creation, SQLite access, fingerprint collection/comparison, project-root safety, discovery outcome classification, immutable history, retry linkage, and structured errors. Svelte owns presentation, selection controls, note forms, filtering, and status display.
- Extend the existing alpha `CREATE TABLE IF NOT EXISTS` schema approach in `src-tauri/src/db/schema.sql`; do not add migrations. Any incompatible local database consequence must be documented as a required reset during alpha rather than handled by silent data rewriting.
- Reuse the v0.0.4 authoritative discovery pipeline, compatibility profile, candidate parser, and fingerprint implementation. Resolve the existing split between persisted `check_for_updates` and event-oriented background discovery before snapshot creation is wired into the UI.
- A normal authoritative candidate review requires the same v0.0.4 evidence gate: supported profile, expected prompt handling, cancellation, and comparable unchanged fingerprints. Unsafe and indeterminate outcomes may still create durable snapshots, but they must remain visibly non-reviewable or limited until a fresh discovery succeeds.
- Stored candidate history must preserve local entry identity separately from provider identity and must keep provider, side, pin, severity, compatibility warnings, and unknown/malformed evidence explicit. Pin is observation, not a decision.
- A review is current only while its relevant project fingerprint matches the stored before-state evidence. Missing, incomplete, or non-comparable evidence invalidates normal review continuation rather than being treated as unchanged.
- User actions must be concurrency-safe and idempotent at the command boundary. Updating a decision or note must not mutate discovery output, timestamps/evidence, or prior operation outcomes. Retry creates a new record linked to its predecessor.
- Follow existing Tauri/Svelte boundaries, typed invocation wrappers, structured command-error translation, shared Button/Modal/Tooltip/toast primitives, keyboard/focus/status/reduced-motion requirements, and the registered-root safety boundary.

### 4. Decisions, Assumptions, and Open Decisions
- **Confirmed handoff assumptions:** v0.0.4 discovery persistence already records explanatory result/candidate JSON and fingerprint comparison; `src-tauri/src/discovery/pipeline.rs` remains the safety authority; the tested profile is narrow and Windows-oriented; no update-application path exists.
- **Confirmed product decisions:** snapshots are update sessions, not releases; Packwiz owns persistent pins; skipped/blocked/deferred are application decisions; failed, partial, cancelled, unsafe, and indeterminate history remains visible; retries create linked new work; current files remain authoritative.
- **Phase 1 decisions closed:** snapshots use `draft -> reviewable -> closed/cancelled/stale`, with unsafe/indeterminate outcomes explicit and non-reviewable; every registered-project discovery attempt creates a durable snapshot; fingerprint rechecks cover the full relevant Packwiz root and incomplete comparisons invalidate; candidate rows use snapshot-local stable IDs, decisions use one current row per candidate with append-only revisions, and notes use scoped stable IDs; project-level notes expose an editable current value while retaining prior values as history; decision/note writes are rejected after invalidation or closure; `check_for_updates` is the single authoritative persisted path and the event-oriented path is constrained to its progress/process events.
- **Additional decisions closed:** unsafe and indeterminate remain `DiscoveryOutcomeKind` values with explicit non-reviewable command/UI behavior rather than duplicate lifecycle enum values; candidate severity is an explicit evidence field defaulting to unknown and is never inferred from version change; the Projects UI will use `check_for_updates` as the authoritative event-aware path; schema additions remain additive with a documented stop-and-delete `settings.sqlite` reset fallback for incompatible alpha databases.
- **Assumptions:** v0.0.4 schema and wire contracts are the starting point; no migration framework is needed in alpha; existing project IDs remain stable; tests can use Packwiz fixtures/fake process seams and must not mutate `../example-modpack`.
- **Risks:** schema relationships may accidentally allow history deletion or decision mutation; stale reviews may be applied in v0.0.6 if invalidation is only UI-level; the remaining event-command migration could create inconsistent snapshots if not completed before UI hydration; malformed/incomplete fingerprint evidence may be mistaken for a current review; severity evidence may be unavailable for tested Packwiz output and must remain unknown.
