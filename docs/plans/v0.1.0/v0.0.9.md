# Specification & Overview

### 1. Scope & Objective
- **Source provenance:** `docs/ROADMAP.md`, section `v0.0.9 - Data Management, Cleanup, and Hardening`; cross-version practices in the same document; repository context in `README.md`, `docs/CM-MODPACK-UTIL-SPEC.md`, and the existing v0.0.8 implementation plan.
- **Goal:** Make application-owned history and removable data manageable without database editing, while preserving external Packwiz project directories, Git history, user export files, and the safety boundaries established through v0.0.8.
- **In-Scope:**
  - Archive, restore, detach, and permanent-delete workflows for supported application-owned records.
  - Dependency and external-reference impact previews before destructive actions.
  - Typed confirmation for permanent deletion.
  - Explicit preservation of external project directories, Git history, and user export files.
  - Detection and presentation of orphaned records and unavailable export destinations.
  - Scoped cleanup for cached provider metadata and obsolete export records.
  - Storage-usage reporting and a clear description of removable data.
  - Keyboard, focus, status-communication, reduced-motion, semantic-status, and color-independent accessibility hardening.
  - Windows path, cancellation, partial-operation, malformed-TOML, disconnected-project, offline-cache, and recovery-warning test coverage.
  - Documentation of supported Packwiz compatibility and known limitations.
- **Out-of-Scope:**
  - Deleting, rewriting, or moving Packwiz project files, Git history, or user-created export files.
  - Database editing as a user workflow, silent data loss, or automatic database migration. The alpha schema-reset rule remains in force if schema changes make an existing local database incompatible.
  - New provider integrations, automatic cache-expiration policy, cloud synchronization, collaboration, private GitHub authentication, unattended updates, or non-Markdown export formats.
  - Changing the v0.0.8 source-of-truth model: Packwiz remains authoritative for current project state, while SQLite owns application metadata, observations, history, caches, and export records.

### 2. Technical Constraints & Architecture
- Rust remains authoritative for filesystem access, canonical paths, registered-root containment, SQLite transactions, record dependency analysis, cleanup eligibility, storage measurement, process/cancellation evidence, and structured command errors. Svelte must use typed Tauri wrappers and must not duplicate safety decisions.
- All destructive workflows must be explicit, previewed, validated at command time, and represented with recoverable-by-default behavior where the source permits it. Permanent deletion must require a typed confirmation and must never target external project directories, Git history, or exported files.
- Preserve the alpha no-migration policy and documented stop-app/reset behavior. Schema compatibility must be bumped to version 4 for v0.0.9; do not rely on `CREATE TABLE IF NOT EXISTS` to retrofit new objects into existing version-3 databases.
- Preserve immutable snapshot, operation, changelog, export, release, and captured-state evidence unless an explicit v0.0.9 lifecycle rule says the application-owned record may be removed. Detach must remove or sever only the selected application relationship, not external files or historical evidence that remains independently valid.
- Keep lifecycle, impact analysis, cleanup, storage reporting, accessibility, and hardening logic in focused Rust/domain, database, typed-wrapper, and Svelte modules rather than consolidating behavior in `lib.rs`, one route, or the database module.
- Use existing shared UI primitives and the documented desktop accessibility standards. Every new destructive or cleanup state needs loading, empty, success, failure, unavailable, stale, and cancellation behavior where applicable.

### 4. Assumptions, Dependencies, Risks, and Open Decisions
- **Assumptions to verify:** v0.0.8 persistence and foreign-key relationships expose enough ownership information to distinguish independently useful history from removable derived records; persisted export observations provide sufficient unavailable-destination reporting without probing or modifying external files; and current UI surfaces can host management actions without replacing existing review workflows.
- **Dependencies:** completed v0.0.8 release, changelog, export, snapshot, operation, and captured-state handoffs; current schema and database reset documentation; registered-root/path-safety contracts; Packwiz compatibility profile; existing fixtures and test harnesses.
- **Primary risks:** deleting a record that is still referenced by a release, snapshot, workspace, artifact, or export; treating a missing project path as permission to delete external content; reporting a cache as removable while an active workflow depends on it; confusing an unavailable destination with an orphaned application record; Windows file locks and path normalization differences; cleanup during concurrent operations; and accessibility regressions caused by dense management tables or modal confirmations.
- **Safety response:** perform native impact analysis against current database state, require stable preconditions, use transactional application-owned deletion only, preserve protected references, return explicit blocked/partial/unavailable outcomes, and test both canonical and equivalent Windows path spellings.
- **Closed decision register:** Schema compatibility uses a sentinel bump to version 4 and the documented manual database reset path for existing alpha databases; physical deletion is limited to provider-cache rows and obsolete export records; immutable snapshots, operations, workspaces, releases, artifacts, revisions, and captured evidence are retained as tombstoned records; cleanup and destructive commands use persisted operation state plus transaction-time reference/freshness predicates, with stale running state recovered on startup; destructive commands require a target/action/scope impact-preview fingerprint in addition to typed confirmation; and unavailable export destinations are classified from persisted export status/path observations without live probing.
- **Non-blocking implementation details:** final remediation wording for orphaned and unavailable records and the exact user-facing copy around the fixed confirmation phrase may be finalized while implementing the already-closed native contracts.

### 5. Closed Decision Register

| ID | Decision | Consequence |
| --- | --- | --- |
| d1-schema | Bump the schema sentinel to version 4 and require the documented stop-app/reset procedure for existing alpha databases. | Do not rely on additive table creation for version-3 databases; update reset documentation and test the incompatible-database path. |
| d2-deletion | Physically delete only provider-cache rows and obsolete export records. | Snapshots, operations, workspaces, releases, changelog artifacts/revisions, and captured evidence remain as tombstoned application records. |
| d3-concurrency | Use persisted operation/cleanup state with transaction-time reference and freshness predicates; recover stale running state on startup. | In-memory coordination alone is insufficient; cleanup and destructive actions must be restart-safe and idempotent. |
| d4-preview | Bind every destructive command to its target, action, scope, and impact-preview fingerprint. | A typed phrase alone is insufficient; changed references or eligibility return a stale-preview error. |
| d5-export-availability | Use persisted export status/path observations only for unavailable-destination classification. | No implicit filesystem probing, external mutation, or claim of current destination reachability. |
| d6-lifecycle-scope | Apply lifecycle actions across application records where each action is semantically valid: modpacks, snapshots, workspaces, releases, changelog artifacts/revisions, and exports. | Phase 1 must produce an action-by-record matrix; invalid combinations are blocked rather than silently coerced. |
| d7-orphan | Define an orphan as a record whose required application parent/reference is missing or tombstoned; external path unavailability is separate. | Orphan remediation must not imply external-file deletion or conflate missing parents with disconnected destinations. |
| d8-confirmation | Use a fixed confirmation phrase containing `DELETE` and the target record identifier, in addition to the preview fingerprint. | The exact phrase is enforced natively and presented accessibly; display-name-only confirmation is not sufficient. |
| d9-storage | Count application-owned SQLite/cache/artifact bytes and report external paths and unavailable sizes separately. | Storage totals must reconcile owned categories without estimating external project or export-file sizes. |
| d10-packwiz-profile | Document the already-tested v0.0.8 Packwiz compatibility profile and its known limitations. | v0.0.9 does not expand Packwiz compatibility scope; unsupported versions remain explicit. |
| d11-provider-retention | Protect provider-cache rows referenced by retained historical evidence; clean only unreferenced cache rows. | Cleanup must report protected references and may not make retained changelog evidence unavailable. |

#### Native lifecycle, impact, and safety rules

- Every destructive request carries target identity, action, cleanup scope where applicable, the current impact-preview fingerprint, and (for permanent deletion) the exact confirmation `DELETE <record-id>`. The frontend may display and collect these values but cannot authorize an action.
- Native preview output must enumerate direct references, retained historical evidence, active operations, removable derived records, external destinations, orphan/unavailable classifications, protected boundaries, and the reason for every blocked or partial outcome.
- Before mutation, Rust re-reads the target row, reference graph, lifecycle/status, active persisted operation state, preview fingerprint inputs, and registered-root ownership under one transaction. Stale fingerprints, changed references, active operations, missing/tombstoned parents, disconnected roots, and unavailable destinations return structured blocked/stale/partial/unavailable errors.
- An orphan is an application record whose required application parent or reference is missing or tombstoned. A missing, disconnected, or unavailable external path is a separate status and never implies permission to remove external content.
- Storage accounting includes SQLite database/WAL/SHM, provider-cache payloads, retained application-owned artifact/export content, and other explicitly application-owned bytes. Registered Packwiz roots, Git metadata/history, and user export destination files are reported separately as external/unavailable and are never estimated as removable.

#### Compatibility and non-blocking copy decisions

- The v0.0.8 Packwiz profile remains the tested local compatibility boundary: safe discovery uses the supported `packwiz update -a` cancellation probe; positional-slug pin/unpin is verified; update application remains refused without a fixture-proven affirmative contract; malformed, unsupported, unsafe, cancelled, and indeterminate outcomes stay explicit.
- Orphan and unavailable wording will distinguish broken application parents from unavailable export destinations and will recommend non-destructive relinking, reconnecting, or record cleanup without implying external deletion.
- Management surfaces will use the existing typed wrappers, shared Button/Modal/Tooltip/toast primitives, and semantic loading/empty/failure/unavailable/stale/cancellation states; exact copy may be finalized during implementation without changing the closed native contracts.
