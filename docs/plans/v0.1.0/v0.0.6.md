# Specification & Overview

### 1. Scope & Objective
- **Source provenance:** `docs/ROADMAP.md`, section `v0.0.6 - Applying Updates and Pin Management`; `docs/CM-MODPACK-UTIL-SPEC.md`, especially Applying Updates, Pins/Skips/Notes, Update Snapshots, Domain Concepts and Business Rules, Data and Lifecycle Expectations, Packwiz integrations, Architecture Guidelines, Long-Running Work and Errors, and the Apply Safety and Pin Safety workflow acceptance criteria; completed `docs/plans/v0.1.0/v0.0.5.md` and the v0.0.4 compatibility boundary as implementation handoffs.
- **Goal:** Apply only explicitly approved Packwiz updates from a current, reviewable snapshot and provide exact-file pin/unpin operations, with Rust-owned safety checks, observable progress, post-operation validation, durable partial outcomes, and accessible review controls. A successful operation must mean that the intended Packwiz state was verified after the process, not merely that a command started or exited successfully.
- **In-Scope:**
	- Define applying/complete/partial/failed/cancelled operation contracts and the relationship between snapshot lifecycle, immutable discovery evidence, operation evidence, and linked retries.
	- Validate the selected snapshot, project, candidate decisions, current project state, compatibility profile, before-state fingerprint, operation exclusivity, and Git conflict/merge/rebase state before mutation.
	- Apply an explicitly confirmed update set through the tested Packwiz profile. Selective application is permitted only if exact targeting is proven; otherwise the operation must require the complete supported Packwiz update set or refuse with a clear reason.
	- Capture command arguments, output, errors, exit status, timing, progress, cancellation, before/after fingerprints, re-read validation, and the resulting snapshot classification.
	- Warn and require acknowledgement when Git or another recovery path is unavailable. Dirty Git trees may proceed after acknowledgement; active conflict, merge, or rebase states block the operation.
	- Implement the audited exact-file positional-slug `packwiz pin` and `packwiz unpin` flows without `--yes`, resolving identity in Rust and re-reading the targeted metadata to verify the resulting Packwiz-owned pin state.
	- Persist immutable operation history, observed before/after evidence, pin observations, failure/partial results, retry linkage, and structured diagnostics using the existing alpha `CREATE TABLE IF NOT EXISTS` approach.
	- Expose typed Rust/Tauri commands and events, typed TypeScript wrappers, and Svelte controls for acknowledgement, apply/cancel, pin/unpin, progress, verification results, and recovery/retry states.
	- Add focused Rust, fixture, process-boundary, persistence, frontend, documentation, and available desktop smoke validation.
- **Out-of-Scope:**
	- Changelog generation/export, Modrinth or CurseForge requests, releases, GitHub enrichment, cleanup/permanent deletion, cloud behavior, unattended updates, automatic rollback, application-created backups, or general dependency conflict resolution.
	- Direct TOML editing or treating SQLite as the authority for current Packwiz configuration or pin state.
	- Applying stale, closed, cancelled, unsafe, indeterminate, unsupported, invalid, externally changed, or incomplete snapshots.
	- Guessing provider identity, source URLs, compatibility, selective-targeting support, or successful state from incomplete evidence.
	- Broadening beyond the tested Windows x86_64 Packwiz 1.1.0 profile unless a separately tested profile is explicitly added.
	- Frontend filesystem inspection, shell/process execution, frontend-created command arguments, or arbitrary project paths.

### 2. Technical Constraints & Architecture
- Packwiz files remain authoritative for current modpack configuration and persistent pin state. SQLite stores operation history and observations, never an application-owned replacement for current files.
- Rust owns project-root authorization, Packwiz resolution and argument vectors, process execution, interactive prompt handling, Git inspection, exclusivity, fingerprints, post-operation parsing/validation, SQLite writes, cancellation, and outcome classification. Svelte owns confirmation, acknowledgement, forms, progress presentation, and accessible status display.
- Apply, pin, and unpin are immutable operation attempts linked to a review snapshot when applicable. Operation state is separate from snapshot review lifecycle and later release status. A mutation operation is globally exclusive across apply, pin, and unpin; discovery keeps its existing coordination policy but cannot overlap a mutation for the same registered project.
- Reuse the v0.0.4 compatibility profile, process runner, fingerprint implementation, v0.0.3 inventory parser, and v0.0.5 snapshot/decision/recheck/retry model. Add a distinct apply path; do not repurpose read-only `check_for_updates` as mutation.
- Mutation command profiles are supported only after disposable fixtures or captured native transcripts prove their arguments, prompts, allowed stdin, exit states, and target behavior. The existing discovery profile does not authorize mutation commands.
- A normal apply requires a current reviewable snapshot, usable before-state evidence, supported compatibility, valid selected decisions, exclusive access, no active Git conflict state, confirmed recovery warning when needed, expected process evidence, and comparable after-state validation. Missing or contradictory evidence produces failed, partial, cancelled, unsafe, or indeterminate history rather than success.
- Snapshot and operation records are append-only for completed attempts. A partial, failed, or cancelled attempt remains inspectable; retry creates a new linked operation/snapshot and never rewrites the original.
- Pin/unpin must target one exact local metadata path selected from native inventory evidence. The audited wrapper uses one positional slug, refuses missing or changed identity, and never passes `--yes`.
- Selective apply is refused unless exact Packwiz targeting is fixture-proven. The complete-set path is eligible only when every actionable candidate is explicitly selected and no candidate is undecided, skipped, deferred, blocked, unknown, or silently excluded.
- Cancellation after mutation may have begun is verified before classification: a proven pre-mutation cancellation is cancelled; possible mutation is partial or indeterminate unless after-state evidence proves complete intent.
- Recovery acknowledgements are single-use records bound to the operation, project fingerprint, timestamp, warning category, and observed recovery state. No-Git/recovery and dirty-Git states warn and require acknowledgement; conflict, merge, rebase, and unavailable Git inspection block.
- Continue the alpha no-migration database policy. Any incompatible local database consequence must be documented as a stop-the-app and reset/delete `cm-modpack-util.sqlite` plus its WAL sidecars recovery path; no silent data rewrite is allowed.
- Preserve keyboard access, visible focus, semantic status, reduced-motion behavior, stable layouts, color-independent meaning, and shared UI primitives from the repository standards.

### 4. Decisions, Assumptions, and Deferred Risks
- **Confirmed handoffs:** v0.0.4 owns the tested Windows x86_64 Packwiz 1.1.0 profile, separated arguments, process events, prompt handling, and fingerprints. v0.0.5 owns durable snapshots, candidate observations, decisions, notes, stale rechecks, and linked retries. No mutation path is currently exposed.
- **Confirmed product decisions:** applying requires explicit review decisions; Packwiz owns persistent pins; snapshot decisions are separate from pins; current Packwiz files are authoritative; partial/failed/cancelled operations remain immutable; no Git is allowed only after explicit acknowledgement; no external project files are deleted by application data management.
- **Decision register:** d1 targeting = refuse unproven selective apply; d2 lifecycle = separate immutable operation attempt; d3 concurrency = global mutation lock; d4 verification = unexpected changes are non-success; d5 acknowledgement = single-use and attempt/fingerprint-bound; d6 profiles = fixture or captured-transcript proof only; d7 cancellation = verify then classify; d8 pin identity = native-resolved entry ID; d9 handoff = audit and gate v0.0.5; d10 UI validation = native checks plus manual matrix; d11 complete-set eligibility = every actionable candidate explicitly selected; d12 persistence failure = indeterminate with recovery guidance; d13 Git = no-recovery/dirty warn, conflict/merge/rebase/unavailable inspection block; d14 pin scope = inventory and review surfaces.
- **Decisions closed before implementation:** selective apply is refused unless exact targeting is proven; the complete-set path requires every actionable candidate to be explicitly selected with no unresolved candidate state; apply, pin, and unpin are separate immutable operation attempts; mutation is globally exclusive; semantic after-state verification is required and unexpected changes are non-success; cancellation is verified before classification; acknowledgements are attempt-bound; mutation profiles require fixture or captured-transcript proof; pin/unpin accepts only a native-resolved entry identity and is available from inventory and review surfaces; v0.0.5 receives a prerequisite audit; frontend validation uses native tests, `npm run check`, `npm run build`, and a documented manual UI matrix.
- **Assumptions:** the existing snapshot schema can be extended additively; project and candidate IDs remain stable through the operation; fixtures can simulate Packwiz mutations without modifying `../example-modpack`; Git inspection can be represented as an existing or newly isolated Rust-owned observation; a live Packwiz smoke pass may remain unavailable.
- **Remaining assumptions:** Packwiz mutation profiles may remain unsupported if disposable fixtures or trustworthy transcripts cannot prove them; live Packwiz smoke coverage may remain unavailable; final SQLite persistence can fail after external mutation and must then produce indeterminate recovery guidance rather than success.
- **Risks:** Packwiz may mutate more files than expected before cancellation; a process exit code may disagree with actual file state; partial writes may leave a valid-looking but incomplete inventory; concurrent external edits may occur between recheck and process start; interactive pin prompts may match multiple paths; UI-only gating could be bypassed unless commands revalidate every condition.
