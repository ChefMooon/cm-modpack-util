# Specification & Overview

### 1. Scope & Objective
- **Source provenance:** `docs/ROADMAP.md`, section `v0.0.4 - Packwiz Compatibility and Safe Update Discovery`; `docs/CM-MODPACK-UTIL-SPEC.md`, especially Packwiz integration, Update Discovery and Review, Domain Concepts and Business Rules, Architecture Guidelines, Security and Privacy, Long-Running Work and Errors, Data and Lifecycle Expectations, and the Discovery Safety workflow acceptance criterion. The completed v0.0.3 plan and its registered-project/inventory contracts are implementation prerequisites.
- **Goal:** Build a controlled, observable, read-only update-discovery path for registered Packwiz projects. The application will identify a tested Packwiz compatibility profile, run `packwiz update -a` in the registered directory, detect and cancel the confirmation prompt by sending only `n`, capture the candidate output, fingerprint the project before and after cancellation, and return candidates only when every safety condition is proven.
- **In-Scope:**
  - Define and record one tested Packwiz compatibility profile: executable/version evidence, supported command form, expected prompt and cancellation output, exit behavior, candidate-output boundaries, and known limitations.
  - Add a Rust-owned observable process runner scoped to the canonical registered project directory, with argument separation, stdout/stderr capture, prompt detection, cancellation, timeout/termination behavior, status, and structured diagnostics.
  - Implement the `packwiz update -a` cancellation probe. Discovery must never send `y` or `--yes`; it sends only `n` after the expected prompt is detected.
  - Capture relevant before/after project fingerprints and validate that cancellation did not change Packwiz state, metadata files, index/config evidence, or relevant directory structure.
  - Parse candidate updates only after compatibility, prompt handling, expected cancellation, and unchanged-state checks succeed. Preserve Packwiz output as authoritative for which candidates were presented and enrich only from already available local inventory evidence.
  - Distinguish supported normal discovery, unsupported compatibility, unsafe prompt/cancellation behavior, changed state, process failure, timeout, and indeterminate outcomes through domain contracts and structured errors.
  - Persist the latest discovery observation/result and activity/operation evidence in SQLite without making SQLite authoritative for current Packwiz files. Continue the alpha `CREATE TABLE IF NOT EXISTS` schema approach; no migration framework is introduced.
  - Expose typed Tauri commands/events and Svelte loading, running, cancellation, success, unsupported, unsafe, indeterminate, unavailable, and failure states for the active registered project.
  - Add focused Rust, fixture, process-boundary, fingerprint, persistence, frontend, documentation, and available desktop smoke validation.
- **Out-of-Scope:**
  - Applying any update, sending `y`, using Packwiz `--yes`, selective update mutation, pin/unpin commands, direct TOML editing, or any other Packwiz file mutation.
  - Snapshot creation, candidate decision persistence, skipped/blocked/deferred notes, review sessions, update application, rollback, changelogs, releases, provider requests, Modrinth/CurseForge/GitHub APIs, and cleanup workflows; these belong to later roadmap milestones.
  - Treating a best-effort parse, an unknown Packwiz version, an undetected prompt, an ambiguous cancellation, or a changed fingerprint as an authoritative candidate list.
  - Running commands against a frontend-supplied arbitrary path, outside the canonical registered project boundary, through a shell/interpreter, or with metadata-derived command arguments.
  - Network access during discovery or provider identity resolution. Local inventory enrichment is limited to evidence already read by the v0.0.3 pipeline.
  - A general Packwiz compatibility matrix or universal output parser beyond the explicitly tested profile.

### 3. Technical Constraints & Architecture
- Packwiz files remain authoritative for current modpack state. Discovery is a controlled observation of Packwiz output, not a second update engine and not permission to edit files.
- Rust owns executable resolution/version probing, process creation, stdin/stdout/stderr, prompt matching, cancellation, timeout/termination, filesystem fingerprints, canonical path enforcement, persistence, operation coordination, and structured error translation. Svelte owns presentation, busy/cancellation controls, candidate filtering/display, and user-facing status copy.
- Process execution must use an explicit executable plus argument vector; no shell interpolation, user-controlled command fragment, or unbounded environment/path injection is allowed. The working directory must be the registered canonical project root.
- The tested compatibility profile must be explicit and inspectable. An installed version outside the profile, missing executable, unsupported command/output shape, or incomplete profile evidence is `unsupported` rather than a best-effort normal result.
- Discovery must never send `y`. `--yes` is forbidden. The runner sends exactly `n` only after the expected confirmation prompt has been detected; prompt absence, duplicate/ambiguous prompts, premature exit, or write failure is unsafe or indeterminate.
- A normal discovery result requires all of: supported profile, expected command launch, candidate/output capture, expected prompt detection, successful cancellation, expected cancellation result, and unchanged post-cancellation fingerprint. Any missing proof prevents authoritative candidates.
- Fingerprints must cover the registered project evidence relevant to update discovery, including `pack.toml`, referenced index, supported metadata files, and relevant directory membership/metadata as defined in Phase 1. Fingerprint collection itself is read-only and must remain inside the registered root.
- Long-running work must not block the UI. Commands/events expose running, output/progress where safe, cancellation, completion, and structured failure states. Concurrent discovery for the same project is blocked; no apply operation exists in this release.
- SQLite stores application-owned discovery observations and immutable process evidence needed to explain outcomes, but current Packwiz files and current inventory remain external authorities. Schema changes use the existing alpha initialization approach and must not claim migration support.
- Discovery performs no network request. Candidate enrichment can use local inventory fields such as local identity, current/available version text when captured, provider, side, pin, source URL, trusted page link, and unknown states; it must not infer version semantics or provider identity.
- Use existing Tauri 2, SvelteKit, TypeScript, Rust, SQLite, registered-project safety boundary, shared UI primitives, opener behavior, settings behavior, and v0.0.3 inventory contracts. Follow keyboard, focus, semantic status, reduced-motion, and color-independent communication requirements.

### 4. Decisions Closed Before Implementation
- **Release boundary:** v0.0.4 ends after safe discovery and candidate observation. No review decision or update application is persisted or exposed beyond the discovery result; those are v0.0.5/v0.0.6 work.
- **Command:** The only discovery command is `packwiz update -a` in the registered directory, using the tested profile's executable and arguments. No `--yes` or shell mode is permitted.
- **Cancellation:** The only affirmative safety behavior is sending lowercase `n` to the detected expected confirmation prompt. The runner never sends `y`; prompt ambiguity or inability to prove cancellation is non-normal.
- **Authority:** Packwiz's presented update list is authoritative for candidate membership. Local metadata may enrich candidates but cannot manufacture candidates or silently resolve unknown identities.
- **Compatibility policy:** One narrow, tested profile is required. Unknown, missing, or outside-profile Packwiz versions are reported as unsupported until an explicitly tested profile is added.
- **Fingerprint policy:** A changed, incomplete, or non-comparable before/after fingerprint rejects normal discovery and is reported unsafe or indeterminate according to the evidence available; it is never treated as no-change.
- **Persistence policy:** Discovery records preserve outcome, profile, command evidence, output/error summaries, cancellation evidence, before/after fingerprint, and candidate observations. They are explanatory observations, not update snapshots or a second current-state authority.
- **Cancellation policy:** User cancellation before prompt handling and process termination after prompt handling are distinct from normal Packwiz cancellation. Both remain visible and cannot produce authoritative candidates.
- **Phase 1 decisions closed:** exact Packwiz executable version/profile, prompt/output corpus, exit code and cancellation markers, output size/time limits, fingerprint file set and normalization, Windows process-tree termination behavior, and the exact candidate grammar accepted for the initial profile.
