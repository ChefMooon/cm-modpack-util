# Specification & Overview

### 1. Scope & Objective
- **Source provenance:** This plan is derived from `docs/ROADMAP.md`, specifically the complete `v0.0.1 - Productize the Existing Template` section, and cross-checked against `docs/CM-MODPACK-UTIL-SPEC.md`, `docs/desktop-ui-standards.md`, and the current repository structure.
- **Goal:** Turn the existing Tauri 2, SvelteKit, TypeScript, Rust, and SQLite starter into a stable CM Modpack Util foundation while preserving the template settings workflows and preparing tested boundaries for project registration in v0.0.2. This release is foundation-only: it does not connect to Packwiz projects, inspect modpack evidence, or perform network or external-file operations.
- **In-Scope:**
  - Rename package, Rust crate, Tauri product metadata, identifiers, window/tray labels, and remaining template copy.
  - Replace the current placeholder application shell with a stable Projects, Activity, and Settings product shell that clearly represents unavailable v0.0.1 capabilities and does not present fabricated project, inventory, update, Git, or Packwiz evidence.
  - Move shared application state and Tauri invocation patterns into product-owned modules while preserving existing settings behavior.
  - Define domain contracts for project references, operations, validation results, structured errors, and operation status without implementing project registration, Packwiz execution, or network access.
  - Establish Rust-owned canonical-path and registered-project scoping contracts for later filesystem work without authorizing arbitrary paths or reading external project directories in this release.
  - Preserve the no-migration SQLite approach and initialize any foundation tables with `CREATE TABLE IF NOT EXISTS`.
  - Add focused tests for database initialization, settings persistence, command error translation, path-boundary rules, and initial frontend routing/shell states.
  - Update documentation needed to explain the v0.0.1 shell, boundaries, and validation behavior.
- **Out-of-Scope:**
  - Network access, Modrinth or CurseForge requests, and provider caching.
  - Packwiz process execution, update discovery, pin/unpin operations, or command mutation.
  - Project registration, Packwiz manifest/index parsing, inventory loading, or filesystem mutation.
  - Snapshot/release/changelog workflows, Git history operations, cloud synchronization, accounts, and collaboration.
  - Introducing a migration framework or silently changing the external project directory.

### 2. Specification Alignment and Traceability

The plan implements only the foundation portion of the specification. The
following rules are binding constraints for every phase:

| Specification requirement | v0.0.1 treatment | Delivery owner |
| --- | --- | --- |
| Packwiz files are authoritative for current external state | Preserve as an architecture contract; no Packwiz read/write path is implemented | Phase 2 boundary checks; v0.0.2+ integration |
| SQLite owns application state and history | Preserve the existing settings database ownership and idempotent initialization; add no premature workflow tables | Phase 3 |
| Rust owns filesystem, process, network, persistence, safety, and error translation | Define Rust-owned contracts and path-scope seams; expose no arbitrary filesystem/process/network command | Phase 3 |
| Svelte owns view state and user-facing status/error states | Implement shell loading, empty, unavailable, and error presentation without simulated success | Phase 2 |
| Local-first operation and minimal Modrinth use | No network access in v0.0.1; document that provider/changelog work begins later | Phase 4 |
| Explicit review, explainability, and no unattended updates | Represent deferred update/review actions as unavailable; do not add controls that imply execution | Phase 2 |
| Filesystem confinement and explicit project registration | Test canonical-path and registered-scope contracts without registering or touching a project directory | Phase 3 |
| Accessibility, visible focus, keyboard navigation, and color-independent meaning | Apply to shell/navigation/settings and verify at the configured minimum window size | Phases 2 and 4 |
| Workflow acceptance criteria | Map registration, discovery, pin, apply, partial outcome, identity, inventory, changelog, release, and cleanup criteria to later roadmap milestones; v0.0.1 verifies only the foundation prerequisites | Phase 1 handoff and Phase 4 exit gate |

Later capabilities remain governed by the specification even though they are
out of scope here: project registration and validation in v0.0.2, inventory and
overview in v0.0.3, controlled Packwiz discovery in v0.0.4, snapshot review in
v0.0.5, update application and pins in v0.0.6, changelog generation/export in
v0.0.7, and release/cleanup capabilities in subsequent roadmap milestones.

### 3. Technical Constraints & Architecture
- Keep the existing Tauri 2, SvelteKit, TypeScript, Vite, Rust, bundled SQLite, shared UI primitives, tray, autostart, opener, and window-state integrations unless a concrete v0.0.1 defect requires otherwise.
- Preserve the source-of-truth boundary: Packwiz files remain authoritative for external modpack state; SQLite owns application metadata and history; Rust owns filesystem access, persistence, safety checks, and domain-oriented Tauri commands.
- Svelte owns view state and user-facing loading, empty, success, unavailable, and error states. It must call Rust through typed/product-owned invocation helpers rather than constructing commands or filesystem paths directly.
- Rust must own canonicalization, registered-project scope checks, persistence access, and structured error translation. No frontend path is trusted as an operation boundary.
- Use the repository's existing feature/component organization and shared design tokens. Keep the shell usable at the configured minimum window size and preserve keyboard, focus, status, and non-color accessibility requirements.
- Retain the current no-migration database policy: schema setup must be idempotent and use `CREATE TABLE IF NOT EXISTS`; any later migration system is a post-initial-release decision.
- Do not present static mock data as successful Packwiz work. v0.0.1 UI states must distinguish foundation/demo content from connected project evidence.
- Exact module names for new domain contracts and product-owned stores/invocation helpers are an implementation decision to close during Phase 1 after inspecting current imports and command call sites.

### Phase 1 Decisions Closed Before Implementation
- **Product identity:** Use `CM Modpack Util`, npm package `cm-modpack-util`, Rust package `cm-modpack-util`, Rust library `cm_modpack_util_lib`, bundle identifier `com.cm.modpackutil`, and version `0.0.1` consistently across source metadata and generated/runtime metadata where applicable.
- **Contract ownership and locations:** TypeScript contracts and invocation/error translation will live under `src/lib/`; frontend shell state will remain route-owned or move into `src/lib/` only when shared. Rust contracts will be split into focused modules under `src-tauri/src/domain/` and `src-tauri/src/safety/`; database ownership remains under `src-tauri/src/db/`.
- **Shell state matrix:** Projects is an empty state with registration unavailable until v0.0.2. Activity is an unavailable/no-operations state. Settings remains functional. Loading and error states are represented for settings and future command boundaries; no connected-project success state is defined in v0.0.1.
- **Persistence:** Keep only the existing `settings` table. Initialization remains idempotent with `CREATE TABLE IF NOT EXISTS`; project and operation tables are deferred until their workflows exist.
- **Windows path policy:** Accept only existing absolute paths that canonicalize successfully under an explicitly registered root. Reject relative, nonexistent, escaping, ambiguous, and unregistered paths. Compare canonical Windows paths case-insensitively. Symlink and junction behavior is explicitly deferred and must not be treated as authorization in v0.0.1.
- **Frontend validation:** Do not introduce a frontend test framework in v0.0.1. Use `npm run check`, `npm run build`, and focused static route/state assertions or scripts where needed.
