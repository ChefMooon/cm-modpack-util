# Specification & Overview

### 1. Scope & Objective
- **Source provenance:** `docs/ROADMAP.md`, section `v0.0.7 - Changelog Generation and Markdown Export`; `docs/CM-MODPACK-UTIL-SPEC.md`, especially Changelog Generation, Provider and Mod Identity Rules, Domain Concepts and Business Rules, Data and Lifecycle Expectations, Non-Functional Requirements, Architecture Guidelines, Technology Decisions and Rationale, and the v0.0.6 snapshot/operation handoff; repository conventions in `AGENTS.md` and `docs/toast.md`.
- **Goal:** Complete the initial update-to-changelog workflow for a selected snapshot. The application must identify changed mods, resolve Modrinth identities with visible confidence and evidence, request only required changelog data, work from exact cached data while offline, persist the original generated artifact and its generation context, support an editable revision, and export Markdown without losing the stored artifact or export history.
- **In-Scope:**
	- Audit the v0.0.6 snapshot, decision, operation, inventory, and typed-command handoffs before adding changelog behavior.
	- Define changelog generation, provider identity, provider version identity, cache, artifact, revision, export, retrieval-status, and structured-error contracts.
	- Identify changed mods from the selected snapshot using snapshot evidence rather than whichever files happen to be current.
	- Resolve Modrinth project and version identities using local evidence first, then targeted Modrinth requests only when generation requires them.
	- Preserve download-provider identity separately from Modrinth changelog-provider identity, including CurseForge-origin and unresolved cases.
	- Cache validated provider responses with retrieval context and timestamps, and permit offline generation only when the cached project/version association is uniquely proven.
	- Generate a reviewable changelog with an optional introduction and explicit missing, ambiguous, unresolved, stale, and failed lookup results.
	- Store generated content, introduction, generation settings, source snapshot, retrieval status, and provider evidence durably.
	- Create editable revisions that preserve the original generated result and identify their source artifact and user edits.
	- Export Markdown to a user-selected destination and retain destination, format, export time, content or hash, and unavailable-file status for each export attempt.
	- Add Rust-owned provider/network/filesystem/database behavior, typed Tauri wrappers, Svelte review/edit/export states, focused tests, and documentation for the supported workflow and limitations.
- **Out-of-Scope:**
	- Applying updates, changing Packwiz files, pin/unpin mutation, releases or captured release-state comparison, GitHub enrichment, cleanup/permanent deletion workflows, cloud synchronization, and unattended generation.
	- CurseForge API access or CurseForge-native changelog retrieval. CurseForge remains a possible download provider whose Modrinth changelog association must remain distinguishable.
	- Provider requests during project open, routine inventory refresh, or rendering a normal inventory view.
	- Guessing a Modrinth identity from weak evidence, treating an ambiguous match as confirmed, or presenting provider data without its association and confidence.
	- Export formats other than Markdown, automatic cache-expiration policy, silent replacement of original generated content, or deletion of user export files.
	- Direct filesystem/network access, shell commands, path construction, or provider selection logic in Svelte.

### 2. Technical Constraints & Architecture
- Packwiz files and v0.0.6 snapshot evidence remain authoritative for current and historical modpack observations. SQLite owns changelog artifacts, provider cache, revisions, exports, and operation history; it does not replace Packwiz or rewrite prior snapshot evidence.
- Rust owns Modrinth network access, exact cache lookup, identity/version matching, filesystem export, SQLite transactions, path safety, progress/cancellation, structured errors, and Tauri command contracts. Svelte owns selection, introduction/revision editing, display of confidence/status, destination selection through supported native APIs, progress presentation, and accessible error states.
- Changelog generation is explicit for a selected snapshot and must not run as a side effect of discovery, project open, inventory refresh, or ordinary snapshot viewing.
- Provider identity is dual: the local Packwiz download provider and local entry identity are preserved independently from the Modrinth project/version identity used for changelog retrieval. Historical evidence must retain the exact local entry/path and match evidence so later local changes do not rewrite the result.
- A Modrinth response is usable for confirmed changelog content only when the provider project and relevant provider version are associated with the local snapshot evidence at an accepted confidence. Exact provider file evidence outranks normalized version matching; missing, ambiguous, unresolved, stale, and failed results remain visible and are not silently converted into confirmed entries.
- Cache records include enough request identity, response/retrieval context, and timestamps to prove exact reuse. Cache freshness rules remain explicit but automatic expiration is deferred; cleanup is a later milestone.
- Generated output and revisions are append-oriented: export never removes or replaces the generated artifact, and re-export creates a new export observation. Database changes must follow the alpha `CREATE TABLE IF NOT EXISTS` policy; incompatible local databases require the documented stop-app/reset path rather than silent migration or data loss.
- Long-running provider work must leave the UI responsive and expose progress, cancellation where practical, completion, partial/failed retrieval, and retry guidance. Keyboard access, visible focus, semantic status, reduced motion, stable layouts, and color-independent status meaning follow `docs/desktop-ui-standards.md`.

### 4. Decisions, Assumptions, and Deferred Risks
- **Confirmed decisions from the sources:** Modrinth is the initial changelog provider; CurseForge API work is deferred; Markdown is the only initial export format; generated artifacts retain editable revisions; cached provider data remains until user cleanup; Modrinth is queried only when generation or required identity resolution needs it; unresolved or ambiguous matches are never confirmed; export does not delete or replace stored artifacts.
- **Handoff assumptions:** v0.0.5/v0.0.6 provide durable snapshots, candidate/decision evidence, operation outcomes, typed domain contracts, project authorization, SQLite access, structured error translation, and shared UI primitives. Phase 0 must verify these assumptions instead of treating the plan as proof.
- **Decisions to close in Phase 1:** the exact changed-mod eligibility rule for review/cancelled/partial/failed snapshots; the accepted confidence states and user-confirmation boundary for Modrinth matches; the exact cache key and version-association proof; the representation of partial generation; whether revisions are immutable append-only records or one editable current revision plus history; the export content-vs-hash retention choice; and the supported native destination-selection boundary on Windows.
- **Risks:** Modrinth search may return multiple plausible projects; local version strings may not map cleanly to provider versions; provider responses may change after caching; a network failure may occur mid-generation; a user may edit a revision while an export is pending; the destination may be moved or deleted after export; database persistence may fail after provider requests; current schema state may differ across existing alpha installations.
- **Safety response:** Never silently accept weak identity, never use stale/inexact cache data as confirmed, keep per-entry status and evidence, persist failure/partial outcomes where possible, keep original artifacts immutable, and report unavailable exports without deleting their history or external files.

### 5. Decision Register - Closed 2026-09-06
- **d1-source-scope:** A reviewable snapshot may generate from its immutable Packwiz discovery candidates. Completed and partial operation snapshots generate from verified applied-change evidence. Current inventory is never used to reconstruct historical changes. Failed, cancelled, unsafe, indeterminate, and stale snapshots are not generation sources unless a later explicit evidence contract permits them.
- **d2-ambiguous-match:** Generation uses two stages. Native preflight resolves identities and persists candidates; ambiguous matches require user confirmation before provider-confirmed retrieval. Unresolved entries remain visible and unconfirmed.
- **d3-cache-rule:** Exact cached responses may be used offline even when stale, but stale retrieval is visible and is not presented as a fresh provider confirmation.
- **d4-export-boundary:** Destination selection uses a native save-file dialog. Rust writes the selected file, and exports may be outside the registered project root. The application never deletes external export files.
- **d5-eligibility:** Preflight/generation accepts reviewable, completed, and partial snapshots. Unsafe, indeterminate, stale, failed, and cancelled snapshots are rejected with a native reason.
- **d6-partial:** One immutable partial generation artifact is stored with per-entry retrieval statuses. Partial output remains reviewable/exportable only with its incomplete state visible.
- **d7-revisions:** Revisions are immutable append-only records with a current-revision pointer. Every revision identifies its source artifact and prior revision where applicable.
- **d8-export-retention:** Each export retains content and a content hash, linked to the exact artifact or revision exported.
- **d9-failure-idempotency:** Every explicit generate/retry creates a new immutable attempt with a request fingerprint. Persistence failure is indeterminate where provider work occurred and never reports a complete artifact without durable artifact evidence.
- **d10-cache-key:** Cache identity includes provider, endpoint/request shape, project ID, version ID, game-version/loader context, and requested changelog fields. Raw response, association evidence, retrieval context, and timestamps are stored separately.
- **d11-version-association:** Confirmed provider content requires exact Modrinth project identity plus a unique provider version association. Exact provider file names are strongest; normalized mod-version matching may produce high confidence only when loader/game evidence or uniqueness removes ambiguity. A project-name match alone is never sufficient.
- **d12-transport:** Modrinth access uses a Rust-owned bounded, mockable transport with per-request timeout, response limits, a three-second delay between online version lookups, visible rate-limit retry guidance, and cancellation between requests. Progress is emitted before and after each lookup and during artifact persistence; an in-flight HTTP request is allowed to finish.
