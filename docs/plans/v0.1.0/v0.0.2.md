# Specification & Overview

### 1. Scope & Objective
- **Goal:** Make local Packwiz projects discoverable and safely registerable so a valid project can be selected, previewed, stored, reopened offline, refreshed, and managed without changing the external modpack directory.
- **Source provenance:** `docs/CM-MODPACK-UTIL-SPEC.md`, especially Project Management, Domain Concepts and Business Rules, Data and Lifecycle Expectations, Architecture Guidelines, Security and Privacy, and the Project Registration workflow acceptance criterion. The v0.0.2 scope is also constrained by `docs/ROADMAP.md`.
- **In-Scope:**
	- Selecting a local directory and validating it without network access, Packwiz update execution, or file mutation.
	- Parsing the required Packwiz evidence: `pack.toml`, its referenced index, supported mod metadata files, top-level Packwiz fields, the index reference and hash fields, and declared `[versions]` values.
	- Returning a registration preview that distinguishes observed Packwiz values from application-owned project metadata.
	- Canonicalizing project paths and rejecting duplicate canonical registrations.
	- Persisting application-owned project metadata, observed Packwiz metadata, derived validation facts, and refresh/open timestamps in SQLite.
	- Opening, editing, archiving, restoring, disconnecting, and explicitly reconnecting projects without deleting external files.
	- Reopening registered projects offline and reporting missing, inaccessible, malformed, or stale external project state clearly.
	- Replacing the current Projects placeholder with loading, empty, preview, success, disconnected, and failure states.
- **Out-of-Scope:**
	- Packwiz update discovery, update application, pin/unpin operations, or any command that mutates Packwiz files.
	- Mod inventory UX beyond the evidence needed to validate registration; full inventory and overview belong to v0.0.3.
	- Network access, Modrinth or CurseForge requests, GitHub integration, changelog generation, snapshots, releases, and provider identity resolution.
	- Automatic deletion of external directories, Git repositories, Git history, or user-created export files.
	- Database migration infrastructure; continue the existing initial-release `CREATE TABLE IF NOT EXISTS` approach unless implementation evidence requires a separately approved decision.

### 2. Technical Constraints & Architecture
- Packwiz files remain authoritative for current external project state. SQLite stores application metadata, observations, validation results, and lifecycle/history records; it must not silently overwrite Packwiz values.
- The Rust layer owns directory selection results, canonical path handling, filesystem reads, TOML parsing, SQLite access, structured errors, and Tauri commands. Svelte owns forms, preview, filtering, lifecycle controls, and user-facing status states.
- All registration and refresh operations must be offline and read-only with respect to the selected directory. No Packwiz process is required for this milestone.
- Registered paths must be canonicalized before duplicate checks and future access. Operations must remain within the registered modpack boundary and preserve the existing safety module's Windows-aware path behavior.
- Required data must be validated before a project is usable. Missing optional values are explicit unavailable/unknown observations; malformed required fields, unreadable files, invalid references, and inaccessible paths are clear validation results rather than partially trusted success.
- Application-owned fields include display name, icon when supported, theme/color, tags, favorite state, description, and lifecycle status. Packwiz-declared name, author, version, pack format, index details, and declared versions are observed evidence and must remain distinguishable in the preview and stored model.
- Existing template settings behavior, shared UI primitives, and product shell remain supported. New commands must use domain-oriented contracts and structured error translation consistent with `src-tauri/src/domain/contracts.rs`.
- **Assumptions:** The currently installed/tested Packwiz file layout is the initial supported profile; exact supported metadata shapes and accepted loader keys will be established from fixtures and repository inspection in Phase 1. The native directory-picker mechanism and TOML parser dependency are implementation discovery items, not pre-decided APIs.
- **Open decisions to close during Phase 1:** supported mod metadata filename/layout variants, exact required-versus-optional validation severity for each Packwiz field, behavior for symlinks/junctions on Windows, whether disconnected records remain visible by default, and the minimum reconnect confirmation needed to preserve project identity.
- **Primary risks:** malformed TOML and hash/index references, Windows canonicalization and case behavior, duplicate paths reached through different spellings, partial reads of a changing directory, and accidental mutation or network access during registration.
