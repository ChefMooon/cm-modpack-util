# Specification & Overview

### 1. Scope & Objective
- **Source provenance:** This plan is derived from `docs/CM-MODPACK-UTIL-SPEC.md`, especially Project Management, Mod Inventory Metadata, Project Overview, Domain Concepts and Business Rules, Data and Lifecycle Expectations, Architecture Guidelines, Security and Privacy, Non-Functional Requirements, and the Workflow Acceptance Criteria. It is constrained by the `v0.0.3 - Inventory and Project Overview` section of `docs/ROADMAP.md` and the completed v0.0.2 plan.
- **Goal:** Make a registered Packwiz project inspectable through a trustworthy, read-only inventory and project overview. The application will re-read current local Packwiz evidence, expose provider/side/pin/source information with explicit unknown states, derive counts from that evidence, show available project/Git facts when they can be established, and report refresh failures without presenting stale or inferred values as current fact.
- **In-Scope:**
	- Read the current supported Packwiz mod metadata for a registered project using Rust-owned filesystem access.
	- Represent local entry identity, displayed name, version, exact metadata path, declared download provider, declared side, valid boolean pin state from local metadata, source URL, and explicit unknown/malformed evidence.
	- Derive provider counts, client/server-side counts, total mod count, and other inventory statistics from the current parsed files.
	- Add trustworthy **Open mod page** actions using explicit or safely derived URLs only; do not issue provider requests merely to render the inventory.
	- Expand the project overview with validation state, Minecraft version, loader/version information, inventory counts, provider and side counts, Git status when available, update counts only when already known from supported local evidence, and recent application activity.
	- Add explicit read-only refresh behavior that re-reads local evidence, updates application observations as appropriate, and clearly reports failures or disconnected state.
	- Keep the alpha SQLite lifecycle intentionally simple: normal startup initializes the current schema, and the developer may delete/reset the local database manually when needed. A user-facing migration or rebuild workflow is deferred.
	- Add the smallest domain-contract extension required to retain current inventory observations and activity facts without making SQLite authoritative for Packwiz state.
	- Replace the Projects placeholder/success surface with loading, empty, valid, stale/refreshing, disconnected, unavailable, and failure states that follow existing accessibility conventions.
	- Add focused Rust, persistence, frontend, and fixture validation plus user-facing documentation for the supported inventory profile and limits.
- **Out-of-Scope:**
	- Packwiz process execution, `packwiz update -a`, update discovery, update application, pin/unpin commands, or any Packwiz file mutation.
	- Modrinth, CurseForge, GitHub, or any other provider API request during inventory rendering or refresh; provider identity resolution and changelog retrieval remain later work.
	- Snapshot creation, update decisions, notes, changelog generation/export, named releases, release comparison, cleanup, permanent deletion, and migration infrastructure.
	- Inferring provider or side values from names, file paths, colors, or external lookups; guessing CurseForge URLs from project IDs alone.
	- Editing the external project directory, Git history, or user-created files; Git support is limited to read-only working-tree status observation.

### 2. Technical Constraints & Architecture
- Packwiz metadata files remain authoritative for current mod inventory, provider declarations, side declarations, pin state, and source URLs. SQLite may cache the latest observation and activity history, but the UI must identify whether values are current, unavailable, stale, or malformed.
- Rust owns registered-project path checks, filesystem reads, TOML parsing, inventory derivation, optional read-only Git inspection, URL trust/allowlisting decisions, SQLite access, and structured Tauri command errors. Svelte owns filtering, selection, presentation, refresh controls, page-opening actions, and user-facing status states.
- Every inventory read must use the existing canonical registered-project boundary. No frontend-provided path, shell fragment, arbitrary file path, or unregistered directory may authorize access.
- Missing, malformed, unsupported, or ambiguous provider/side/source values must remain explicit unknown or unavailable observations. `pin = true` is known local Packwiz evidence for pinned state, and an absent `pin` field is known local Packwiz evidence for unpinned (`false`) state. A present malformed, unsupported, or ambiguous pin value remains explicit unknown or unavailable. Counts must distinguish known values from unknown values rather than silently assigning a category.
- **Open mod page** must be enabled only for an explicit trustworthy URL or a safely derived Modrinth project page from a known Modrinth identity. A CurseForge project ID without a trustworthy slug/page URL is insufficient. Opening a known URL may use the existing opener integration and must not call a provider API.
- Opening a project performs the existing read-only local revalidation and updates the open timestamp; explicit Refresh performs the full inventory read and persists current inventory observations. Neither operation runs Packwiz, makes a network request, or mutates Packwiz files. Long-running reads expose a busy/progress state and structured completion/failure results.
- Preserve the existing Tauri 2, SvelteKit, TypeScript, Rust, SQLite, shared UI primitives, settings behavior, and product shell. Database migration, backup, and rebuild UX are deferred while the project is in alpha.
- Use a strict evidence profile: local metadata is observed only when supported fields are valid, except that the optional absent `pin` field explicitly means unpinned (`false`). Provider/side/source/page values that are missing, malformed, ambiguous, unsupported, or not explicitly evidenced remain unknown or unavailable. The application never writes the `pin` field directly.
- Activity is limited to a minimal application-owned project log for registration, open, refresh success/failure, metadata changes, and lifecycle changes. Git is limited to read-only repository presence, clean/dirty/unknown state, and conflict/merge/rebase indicators where reliably available; commit history, tags, reconstruction, worktrees, and release provenance are deferred.
- The exact inventory field mapping, count semantics, Git status evidence, URL trust rules, refresh consistency behavior, and frontend module split are Phase 1 decisions now closed below and must not be weakened during implementation.

### 3. Decisions, Assumptions, and Risks
- **Confirmed assumptions:** The v0.0.2 supported profile remains the initial Packwiz input profile; registration has already validated `pack.toml`, its referenced index, and supported `*.pw.toml` metadata. The current project may be disconnected or malformed after registration and must remain inspectable as an explicit unavailable/failure state. Provider counts and side counts are derived, not manually edited. No provider request is needed to display local inventory.
- **Closed decisions:** Opening preserves the v0.0.2 read-only revalidation behavior; explicit Refresh owns full inventory persistence. v0.0.3 implements a minimal project activity log. Packwiz fields use strict local evidence only, with no best-effort inference. The existing database is rebuilt only after a warning and explicit confirmation, with a timestamped backup created before replacement and no action when declined. Git exposes read-only working-tree status only. Inventory observations use explicit current, stale, unavailable, malformed, and unknown states; exact field and count mappings are recorded in Phase 1 fixtures/contracts.
- **Deferred decisions:** Broader Packwiz layouts, CurseForge API integration, private GitHub authentication, cache expiration, commit-based release reconstruction, and application-created backups as a recovery replacement remain outside v0.0.3.
- **Primary risks:** changing or partially written TOML during refresh, malformed metadata that looks superficially valid, accidental provider/side inference, unsafe path or URL handling on Windows, stale observations being presented as current, and Git or opener behavior exposing an unintended path or URL. Tests must cover each risk before the exit gate.
